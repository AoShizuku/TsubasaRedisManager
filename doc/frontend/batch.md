# 批量操作

覆盖：`src/components/dialogs/BatchTtlDialog.vue`、`src/components/dialogs/BatchDeleteDialog.vue`、`src/stores/ui.ts`（`BatchTtlTarget`、`BatchDeleteTarget`）、`src/lib/ttl.ts`（`TTL_CONDITIONS`、`supportsTtlConditions`）、`src/components/sidebar/KeyTree.vue`（批量入口）、`src/stores/sessions.ts`（`forgetPrefix`、`invalidateKeyspace`）、`src/styles/overlay.css`（`.bulk-*`）

批量设置 TTL 与批量删除共用一个骨架：作用范围怎么表达、数量未知时怎么诚实、危险怎么说出来、
结果怎么反馈。以后的批量功能照此办理。

后端那一半——任务形状、进度口径、试算、模式原样——见 [backend/tasks](../backend/tasks.md)；
集群下怎么发见 [backend/cluster](../backend/cluster.md)；表格多选见 [key-browser](key-browser.md)「多选」。

## 批量不是 for 循环

单 key 的 TTL 编辑是 popover（`TtlChip.vue`），因为它**高频、低风险**，弹模态太重。
批量把这两个判据都反了过来：

| | 单 key | 批量 |
|---|---|---|
| 频次 | 高 | 低 |
| 风险 | 改错一个，看一眼就发现 | 改错十万个，一分钟后库空了 |
| 撤销 | 再点一次改回来 | **没有撤销**——过期的 key 已经不在了 |
| 反馈 | 立刻，chip 就在眼前 | **延迟且不可见**——点下去界面什么都不变 |

所以批量一律是 **modal**（`Dlg`）。这张表留在这里，是为了不让下一个人看着单 key 的 popover
觉得批量也该用 popover。

最后一行最要紧：**批量 TTL 的破坏是延迟发生、不可见、不可撤销的。** 批量删除至少当场可见——
删完树里就少了（见「删完裁树」）。批量 TTL 点下去界面什么都不会变，危险只能在点之前说出来。

两种 TTL 编辑共用 `TtlModePicker.vue`（`PERSIST` / `EXPIRE` / `EXPIREAT` 三种模式），批量只多一组条件。

## 两个入口

| 入口 | 作用范围 | 场景 |
|---|---|---|
| **Key 浏览器表格**：勾选若干行 → 操作条的「设置 TTL…」/「删除…」 | 显式 key 列表 | 按 TTL 列排序，找出快过期的一批，续命或删掉 |
| **树里右键 namespace** →「批量设置 TTL…」/「批量删除…」 | `matchPatternFor` 拼出的模式，如 `cache:page:*` | 给整个前缀补 TTL，或整片删掉 |

两个入口 × 两个功能，四条路通向两个对话框（每个功能一个）。入口决定的只是打开时预选哪种作用范围
（`BatchTtlTarget.scope` / `BatchDeleteTarget.scope`）；表格入口同时把浏览器当前的筛选模式预填进模式框。

第一条是 Key 浏览器存在理由的闭环：「哪些 key 马上要过期」在树里查不到，查出来之后要能**就地处理**，
否则用户还得把 key 名抄到别处去。

树里的 key 行如果同时是前缀（`user` 与 `user:1` 并存），或者右键落在合并行的中间段，菜单里也有
「批量删除…」：那是从树里删掉 `user:*` 的唯一入口，否则用户只看得到一个删 `user` 这一个 key 的「删除」。

**树不做多选**，这是取舍不是遗漏：

- 树里的行可以是紧凑合并行，一行代表好几段路径（`cache:page:home` 显示成一行）。勾它是什么意思——
  勾这个 key，还是勾这个前缀下的全部？
- 多选态要和展开 / 折叠共存：折叠一个已经勾了子节点的命名空间，那些选中还算数吗？
  滚出视口呢（树是虚拟化的）？
- 分段命中（右键 `cache` 段拿 `cache:*`）已经给了树一条通往批量的路，而且它表达的是「一个范围」，
  比「一堆勾」更贴合树的语义。

树负责定位，表格负责分析与处理。

## 作用范围

```
作用范围
  ● 已选中的 128 个 Key
  ○ 匹配模式  [ cache:page:*              ]  [试算]
```

**显式列表**数量确定，直接写出来。没有勾选时这一项置灰并注明。

**模式**的数量未知——SCAN 之前谁也不知道命中多少。硬标准是：

> **不要编数字。** 界面上出现的每个数量都必须是真的。

所以模式下写「数量未知，执行中可随时在状态栏停止」，旁边给 **[试算]**。试算出数之后改成
「试算命中 N 个 Key」，按钮与页脚的文案也跟着用这个数；**改动模式框就作废试算结果**——
上一次的数字不再对应任何东西。试算只对模式开放，显式列表的数量本来就确定。
试算为什么可信见 [backend/tasks](../backend/tasks.md)「试算」。

### 已加载不等于全部匹配

表格只能勾**已加载的行**——SCAN 是增量的，表格里有 500 行不代表库里只有 500 个匹配。
所以操作条在计数旁写「仅限已加载的 N 行」，与表格底部「排序只作用于已加载的 N 个 Key，扫描尚未完成」
是同一个诚实标准：**这张表看到的不是全部。**

想对「全部匹配」动手，就切到模式作用范围——那才是表达「全部」的正确形状。

## 危险写在按钮上

Redis 红只用于品牌与危险，所以按钮颜色跟着语义走。页脚（`.bulk-note`）同时写出后果，并用 `.bulk-cmd`
把将要执行的命令形状摆出来（如 `EXPIRE <key> 3600 NX`、`SCAN MATCH cache:page:* → DEL`）——
后果与命令都要在按下之前就在眼前。

### 批量 TTL

批量 TTL **有时危险有时不危险**：

| 情况 | 按钮 |
|---|---|
| 不过期（`PERSIST`） | `primary`「取消过期时间」 |
| 到期时刻较远 | `primary`「设置 TTL」 |
| 到期落在「即将过期」阈值内 | **`dangerSolid`**「设置 TTL（128 个 Key 将在 1 分钟内消失）」 |
| 绝对时刻不晚于现在 | **禁用**，页脚红字「绝对时刻必须晚于当前时间 —— 这等于立即删除……」 |

阈值是设置项 `ttlSoonThreshold`（默认值以 `stores/settings.ts` 为准），与 TTL chip 的「即将过期」同一个值。
数量未知时按钮写「匹配的 Key 将在……内消失」，不编数字。

最后一行是硬拦：`EXPIREAT` 一个过去的时间戳等于立即删除。前端拦了，后端还会再拦一次，
见 [backend/tasks](../backend/tasks.md)「批量 TTL 的后端校验」。

### 批量删除

删除永远危险，按钮一律 `dangerSolid`，变的只是它说了多少：

| 情况 | 按钮 |
|---|---|
| 显式列表 | 删除 128 个 Key |
| 模式，已试算 | 删除 12,431 个 Key |
| 模式，未试算 | 删除匹配的全部 Key（数量未知） |
| 模式恰好是 `*` | **删除 db0 的全部 Key** |
| 模式为空 / 一个都没勾 / 只读会话 | 禁用 |

`*` 那一行是把话说全：`*` 不是「删一批」，是清空这个 DB。数字说不出这件事（试算出来的一千万
只是个大数字），DB 号说得出来。同理，树里的 **DB 行不给批量删除**——那是 `FLUSHDB` 的形状，
不该由一个顺手的右键做到。

### 试算不强制

删除不可撤销，但**不强制先试算**：

1. 试算是完整跑一遍 SCAN。对一个百万级前缀，强制试算等于把工作量翻倍。
2. 「批量不是 for 循环」那张表已经认定：批量删除的破坏当场可见，比批量 TTL 那种延迟、不可见的破坏**轻**。
   批量 TTL 都没强制，删除更没理由。

危险靠按钮文案说清楚，不靠多加一道门。

## 条件 flag

```
条件
  ● 总是设置
  ○ 仅当前没有过期时间时设置                  NX
  ○ 仅当会延长现有过期时间时设置              GT
  ○ 仅当会缩短现有过期时间时设置              LT
```

条件不是可选项。没有条件的批量 TTL 会把范围内**已经设好的 TTL 全部覆盖**：给 `cache:*` 补 TTL，
把里面本来设了 7 天的 key 全改成 1 天。

| flag | 场景 |
|---|---|
| `NX` | 只给还没有 TTL 的 key 设——「补上漏设的」，排查内存泄漏的第一动作 |
| `GT` | 只延长不缩短——续命，不误伤设得更长的 |
| `LT` | 只缩短 |

`XX` 在类型里声明了（`TtlCondition`），界面上不放：它（只改已经有 TTL 的）在批量场景里没有明确用途，
多一个选项就多一次误选。选项表以 `TTL_CONDITIONS` 为准。

低版本服务端收到条件 flag 直接报错，所以**在界面上置灰并说明**，不等用户点下去才报错——
与 [backend/codec](../backend/codec.md)「归属切分」对编解码器矩阵的处理是同一条规矩。
判断依据是会话的能力 `expireConditions`：条件区按它的 `usable` 置灰，提示原样显示它的 `reason`
（版本太低、读不到版本、认不出的实现，文案都由后端给）。不按 `redis_version` 判——它在 Valkey 等兼容实现上
会判反。这一项「未知时禁用」，后端 `start_batch_ttl_task` 守同一条规则。见 [backend/capabilities](../backend/capabilities.md)。

`PERSIST` 没有条件参数，选「不过期」时条件区整块禁用；后端对带条件的 `PERSIST` 同样拒绝。

## 结果反馈

- **任务一启动就关对话框。** 不让一个 modal 挂在那里几分钟。
- 进度走状态栏的任务条（「N 个后台任务」+ 每个任务的停止按钮），任务名经 `TASK_TYPE_LABEL` 译成中文。
- 结束后 toast：
  - 批量 TTL：「已设置 N 个 · 未变更 M 个 · 失败 K 个」（零项省略），有失败用 `danger`。
    「未变更」为什么必须说出来，见 [backend/tasks](../backend/tasks.md)「进度口径」。
  - 批量删除：「已删除 N 个 Key」，不报「扫到了但没删掉」的差值，理由同上。
  - 停止时用 `warn` 写出停下之前已经完成的个数；失败时用 `danger` 带上后端的错误信息。
- **刷新受影响的读数**：`sessions.invalidateKeyspace` 递增会话的 keyspace 版本号，已打开的 key 标签页
  与 Key 浏览器 watch 它重新取数，否则 TTL chip 与 TTL 列显示的是陈旧读数。停止之前改掉的是真改了，
  所以停止也要刷。
- **不触发「写入即转正」。** 那条规则的判据是「你对**它**动过手」；批量是对一个范围动手，
  把碰巧打开的预览页转正会莫名其妙。只刷读数，不改标签状态。
- **树不跟着版本号刷新**——它是显式加载的快照，重扫是重操作，界面上另有「重新扫描」。
  批量删除因此要自己裁树，见下一节。

## 删完裁树

「批量删除较轻」的全部依据是**它当场可见**。树不跟着 keyspace 版本号刷新，所以这个功能必须自己把
那一片摘掉，否则那个论证是假的：删完 `cache:page:*`，树上原封不动，点进去每个 key 都报不存在——
看起来就是坏了。

树入口在 `BatchDeleteTarget.prefix` 里带上**字面前缀**（含尾随分隔符），任务完成后
`sessions.forgetPrefix` 按 `startsWith` 裁掉已加载的 key。它不是 `pattern` 的副本：`pattern` 已经被
`matchPatternFor` 转义过，拿它去比字符串会把 `evil\[ab\]:` 当成真实前缀。

为什么是 `startsWith` 而不是 glob 匹配：模式是从前缀生成并转义过元字符的
（[key-tree](key-tree.md)「前缀生成模式必须转义 glob 元字符」），`前缀 + 分隔符 + *` 的语义**就是**
「以这个字面前缀开头」，`startsWith` 与它精确等价。

三个前提缺一不可，少一个树就会撒谎：

| 前提 | 少了会怎样 |
|---|---|
| 只在 `completed` 时裁 | `cancelled` / `failed` 只删了一半，抹掉整片是撒谎；这两种情况维持现状，用户用「重新扫描」对齐 |
| 模式没在对话框里被编辑过 | 把 `cache:page:*` 改成 `cache:*` 再删，裁的还是 `cache:page:`，树上留下一堆不存在的 key |
| 前缀非空 | `startsWith('')` 恒真，整棵树的已加载 key 会被一起裁掉 |

最后一条在两处守：`openBatchDeleteFor` 收到空前缀直接返回，`forgetPrefix` 自己也拒绝空前缀。
`ctxSegment?.path ?? ''` 这个写法在「在 Key 浏览器中打开」上默认值是良性的（`*` = 看一眼整个 DB），
在批量删除上是清空 DB。现在的菜单走不到空串，但**不可撤销的操作值得让它不可表达**。

表格入口传 `prefix: null`：那里的模式是用户手输的 glob，裁不出一片字面前缀；刷新版本号就够了。

## 只读

- 两个入口在只读会话上置灰，title 写「该连接为只读模式」——置灰并说明原因，而不是默默不响应。
- 表格的复选框在只读下**照常可用**：选中本身不是写操作，只有操作条里的按钮置灰。
- 对话框的提交按钮同样判 `Session.readonly`。只读依据只认会话，见 [backend/sessions](../backend/sessions.md)「只读属于会话」；
  后端在任务启动时再拦一次。
- 后端对只读会话放行试算（[backend/tasks](../backend/tasks.md)「试算」），但入口整个置灰，
  所以只读会话上目前没有界面路径能发起试算。

## 不做

- **树多选**，理由见「两个入口」。
- **强制先试算**，理由见「试算不强制」。
- **对话框之外再套一层 `ui.confirm`。** 对话框本身就是那次确认。两层模态是噪声，第二层几乎一定被
  无脑点掉，反而稀释第一层的注意力。表格入口因此也不再自带确认，两个入口都走同一个对话框。
- **DB 行的「批量删除」**，理由见「批量删除」。
- **前端写 glob 匹配器来裁树。** 那是第二份实现，两边对 `[]` 的口径迟早漂，漂的后果正是树上留下
  不存在的 key。见「删完裁树」。
