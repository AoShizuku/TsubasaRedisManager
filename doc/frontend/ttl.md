# TTL

覆盖：`src/components/keys/TtlChip.vue`、`src/components/keys/TtlModePicker.vue`、`src/lib/ttl.ts`（`useTtlCountdown`、`useTtlDraft`、`ttlCommandFor`、`TTL_UNITS`、`TTL_PRESETS`）、`src/lib/format.ts`（`formatTtl`、`ttlState`）、`src/components/keys/KeyTab.vue`（chip 的位置与重同步、失效态）、`src/components/keys/useKeyMeta.ts`（`missing`）

单 key 的 TTL 是一个 chip 加一个 popover。批量设置 TTL 是另一类操作（modal、条件 flag），
见 [batch](batch.md)「批量不是 for 循环」；两者共用 `TtlModePicker.vue` 与 `useTtlDraft`。
树与 Key 浏览器里的 TTL 见 [key-tree](key-tree.md)「树里默认不显示 TTL」与 [key-browser](key-browser.md)「TTL 列」。

## TTL 是控件，不是元数据

TTL 和 `编码 listpack`、`slot 9241` 不是一类东西：

- **唯一会自己变化的**元数据，其余全是静态的；
- **唯一自带破坏性的**：归零 key 就消失，排查缓存问题时这是第一眼要看的；
- **唯一被高频修改的**：encoding 和 slot 只读；
- **它的缺席本身就是信号**：本该过期却显示「不过期」，是很常见的内存泄漏征兆。

所以它不和别的元信息一样做成灰色小字，而是一个**既是读数又是入口**的控件。

## 位置：操作组的最前面

```
user:profile:1002  [HASH]
9 字段 · 1.24 KB · 编码 listpack · slot 9241 · prod-east / db0

                            [⏱ 23:41:07 ▾]  │ [刷新][重命名][复制][⋯] │ [删除]
```

它是入口，所以放在右侧操作组里（`KeyTab.vue` 的 `.kh-act`）；元信息行不再重复 TTL。

## Chip 的状态

状态由 `ttlState` 判定，文案由 `formatTtl` 给出。

| 状态 | 呈现 | 说明 |
|---|---|---|
| 未知 | `—` | 元信息还没回来 |
| 不过期 | `不过期`，中性灰，界面字体 | `TTL` 返回 `-1`。它是状态词，不是数据 |
| 倒计时 | `23:41:07`，超过一天前置天数；等宽 + `tabular-nums` | 不用等宽数字的话每秒都在抖 |
| 即将过期 | 琥珀色 `--warn` | 剩余秒数不超过「即将过期阈值」（`ttlSoonThreshold`，设置 → 通用）。此时它应该是整个头部最扎眼的元素——它确实马上要消失了 |
| 已过期 | `已过期`，红色 | 本地倒计时归零 |

元信息取回时 `TTL` 返回 `-2` 或 `TYPE` 为 none（`useKeyMeta` 的 `missing`），整个标签页换成「该 Key 已不存在」，
给「重新检查」与「关闭标签页」——不要继续显示一张陈旧的表。本地倒计时归零只改 chip，标签页要等下一次重同步
才切到这个状态，见 [backlog](../backlog.md)「TTL 读数只在本地倒数」。

## 点开是 popover，不是 modal

改 TTL 是高频、低风险操作，弹模态太重。

```
┌──────────────────────────────┐
│ 过期时间                      │
│  ○ 不过期            PERSIST │
│  ● 相对  [ 86400 ] [秒 ▾]    │
│  ○ 绝对  [2026-07-26 10:21]  │
│  快捷  5分 1时 1天 7天 30天   │
│ ──────────────────────────── │
│  到期于 2026-07-26 10:21:20  │
│  EXPIRE user:profile:1002 …  │
│              [取消]  [应用]   │
└──────────────────────────────┘
```

### 三个模式直接对应三条命令

| 模式 | 命令 |
|---|---|
| 不过期 | `PERSIST key` |
| 相对 | `EXPIRE key <seconds>` |
| 绝对 | `EXPIREAT key <unix-timestamp>` |

**把即将执行的命令原样显示在底部。** 这个工具的调性是把 Redis 的真相摊给你看，而不是包一层黑箱，
顺带也在教用户 Redis 本身。显示真相不等于由前端发命令：底部那行只是 `ttlCommandFor` 拼出来的预览，
真正执行的是 `redis_set_key_ttl`，前端只给模式和数值，命令由后端拼。

### 底部永远显示换算出的绝对时刻

TTL 最常见的翻车是单位和基准搞混——秒还是毫秒、从现在算还是从纪元算。无论用哪种输入方式，
底部都给出「到期于 …」这个人类可读的结果时刻，这类错误直接归零。换算集中在 `useTtlDraft`，
单 key 与批量共用，两边各算一遍的话，这类错迟早只在其中一边被修掉。

绝对时刻早于当前时间等于立即删除，不能悄悄通过：底部换成红字提示，「应用」置灰。

### 其余细节

- **单位下拉**（秒 / 分 / 时 / 天，`TTL_UNITS`）避免心算。草稿里数值与单位分开存，填 `1 天` 重绘后不会变成 `86400 秒`；发给后端前才换算成秒。
- **快捷预设**（`TTL_PRESETS`）覆盖大多数场景，一次点击完成。
- 每次打开都按当前剩余值重建草稿，不残留上一次的输入。
- **只读会话**下 chip 照常显示读数（读值本身有价值），只是点不开，title 说明「该连接为只读模式」。
- **应用成功后 chip 立即切到新值**，不等下一次刷新；同时把预览页转正，见 [tabs](tabs.md)「写入即转正」。

## 倒计时在本地递减，不轮询服务端

每秒对每个打开的 key 发一次 `TTL` 是错的：开十个标签页就是 10 rps 的无谓流量，跨时区、时钟漂移时反而更不准。

`useTtlCountdown` 的做法：

1. 拿到一次 TTL，记下这个值与取到它的时刻；
2. 按单调时钟（`performance.now()`）本地递减渲染。不用墙钟，系统时间被调整时倒计时才不会跳变；
3. 只有正数才起每秒一次的定时器，`-1` / `-2` 是静态的。

读数在这些时机与服务端重新同步（都经 `KeyTab.vue` 重取元信息，新值进来倒计时就从新值重起）：

- 点刷新按钮；
- 对这个 key 的写操作成功之后（改值、重命名）；
- 批量任务结束、会话的 keyspace 版本号递增之后（批量可能正好覆盖了这个 key）；
- 切回这个标签页：主区只渲染活动标签页，切回来就是重新挂载、重新取元信息。

窗口重新获得焦点**不**重同步。

## 不做

- **轮询服务端刷新倒计时。** 理由见「倒计时在本地递减，不轮询服务端」。
- **TTL 编辑做成 modal。** 单 key 的 TTL 高频、低风险；modal 留给批量，见 [batch](batch.md)「批量不是 for 循环」。
- **TTL 放回元信息行。** 它是控件，不是元数据，见「TTL 是控件，不是元数据」。
