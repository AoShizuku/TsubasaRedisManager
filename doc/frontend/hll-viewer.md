# HyperLogLog 查看器

覆盖：`src/components/keys/viewers/HllViewer.vue`、`src/components/keys/KeyTab.vue`（HLL 分发、中性 tag、`HLL` 元信息格）、`src/styles/hll.css`、`src/styles/tokens.css`（`--hx-*`）

视觉稿见 [doc/fe_ref/07-hyperloglog.html](../fe_ref/07-hyperloglog.html)。识别探针、命令与 inspect 的降级分层见
[backend/hll](../backend/hll.md)。

## 首先是防损坏

HLL 的 `TYPE` 就是 `string`。不单独识别的话，HLL key 会落进 StringViewer：用户看到一坨 base64
（头部之后全是二进制寄存器），而且**编辑器是可写的**——dense 恒为 12,304 B，远低于
`DEFAULT_VALUE_LIMIT`，截断契约的只读不触发。手改几个字节保存，`SET` 原样写回，这个 key 就废了。

所以这个查看器首先是一次**防损坏**：识别出来，挡住裸编辑；其次才是把基数、结构这些真正有用的信息呈现出来。
`KeyTab.vue` 在 StringViewer **之前**按 `meta.hll` 分发到 `HllViewer`——顺序反过来，就是把这条路径重新打开。

## 定位：string 的子形态

后端只给 `KeyMeta` 加一个 `hll`，`key_type` 仍是 `string`。整个类型体系——`keyTypes.ts` 的联合、
`connection.rs` 的 `size_command`、批量操作、导出、CLI——都没有 HLL 的特例：对它们而言 HLL 本来就是 string，
这是 Redis 自己的模型，如实沿用。

界面表达：

- 元信息头的 `TypeChip` 保持 `STRING` 与 string 类型色，旁边加一枚**中性 tag**「HyperLogLog」。
- keymeta 行多一格 `HLL dense` / `HLL sparse`。
- **不新增颜色**，类型色仍只出现在三处。树与列表的圆点一直是 string 色，因为 SCAN 不识别 HLL
  （[backend/hll](../backend/hll.md)「识别：打开 key 时 GETRANGE 探针」）。

## 仪表盘

HLL 不存元素，成员不可枚举、不可检索、不可删除——所以主体不是数据表而是**仪表盘**：

- 估算基数大数字（`--fs-32` + `tabular-nums`）。
- 标准误差 ±0.81% 如实标注；绝对量足够大时（`errorAbs`）一并给出「约 ±N」。
- 一段说明「为什么没有成员表」，并指出合并多个 HLL 用 CLI 的 `PFMERGE`。
- 唯一的写操作 `PFADD` 在工具条，与 Hash / Set 的「添加」同位。输入框按 UTF-8 文本提交。

底部状态行写着 `PFCOUNT` 在打开与刷新时执行，以及它的副作用：「计数会刷新服务端头部的 8 字节基数缓存：
物理字节可能变化，逻辑值不变」（语义见 [backend/hll](../backend/hll.md)「PFCOUNT 的写语义」）。写出来，是免得
「只读会话导出前后字节不一致」被当 bug 报，或者反过来有人以「只读要纯」为由把基数显示做残。

状态行右侧的「只读会话：可计数，不可添加」角标**只在只读会话渲染**——它是对当前会话的陈述而不是能力说明书，
对可写会话说「不可添加」是假命题。只读时它有真实价值：解释了为什么 `PFADD` 输入框禁用而基数照常显示。

## 结构查看器

结构查看器（解析 / 原始两个视图）是**一个组件的两种排布**，同一块 DOM 靠 `.is-main` 切换：

- **健康态** = 底部抽屉，默认收起；「解析」为主、「原始」为辅。展开时才去取 inspect 与原始字节。
- **回退态** = 顶到主体，banner 写出服务端的原话；「原始」为主，「解析」降级为逐字段 ✓ / ✗——
  头部往往还是好的，坏的只是长度或操作码（[backend/hll](../backend/hll.md)「inspect：降级逐字段」）。

「校验失败」不是孤立页面，是同一查看器的退化档位——与 [backend/codec](../backend/codec.md)「硬规则」
「解码失败不妨碍看值」同构：看不懂的时候，字节是唯一诚实的展示，并且要如实说明为什么看不懂。

**回退态的判据**是 `PFCOUNT` 报错、且措辞匹配 `WRONGTYPE|INVALIDOBJ`（`corrupted`）。**两种都要认**：
长度或头部没过校验是 `WRONGTYPE`，sparse 操作码在计数中途坏掉是 `INVALIDOBJ`。网络断掉、会话失效同样让
`PFCOUNT` 失败，那不是损坏，走普通错误行 + 重试，不进红色 banner。

反过来，**计数正常不等于数据正常**：坏 sparse 加一个仍标有效的基数缓存，`PFCOUNT` 安静地返回旧数，
查看器不进回退态，只有解析视图会显示「寄存器无法展开」。

### 热力图是寄存器区的本体表示

一寄存器一像素（128 × 128 canvas，零依赖），灰度随寄存器值、0 为纯黑（映射以 `drawHeatmap` 为准）。
截断缺失的段留透明，容器的斜纹底透出来——**缺数据与值为零是两回事**。均匀噪点即健康，色块与条纹是损坏的形状。

它承担诊断职责的决定性理由：**服务端对 dense 只校验总长度**（`isHLLObjectOrReply`）。长度合法而寄存器是垃圾的值
不会报错，只会安静地给错数——这类损坏 raw hex 和错误提示都抓不到，热力图是唯一能让它显形的东西。

### 解说词按非零率分档

「均匀噪点即健康；大块纯色是损坏」这套阅读语法**只在高填充时成立**。一个十几个元素的 HLL 画面 99.9% 纯黑，
对着它展示这句话，健康的 HLL 会被读成坏的。所以非零率低于 `LOW_FILL_RATIO`（一成）时换用低基数解说
（「以纯黑为主是正常的；亮点 = 被命中的寄存器，应均匀散布」），并且不显示「平均」——四舍五入成 0.0，没有信息量。

### 6-bit 示意只对 dense 成立

sparse 的字节是操作码流，不是 6-bit 打包。所以寄存器区旁的三字节跨界示意**只在 dense 显示**，
寄存器区标题也按 encoding 措辞：sparse 写「N B 操作码流 · 展开为 16,384 寄存器」，dense 写「N B · 16,384 × 6 bit」——
两种写法互换，标题里的两个数字就自相矛盾。

### 染色与 BIN

头部四字段（魔数 / encoding / 保留 / 基数缓存）各配一色：hex 底色与字段表色块同色对照。图例色是 `--hx-*`
专用小色板，**不动 Redis 类型色**。解析视图的头部 hex 从 inspect 结果无损重建（魔数与保留字节是常量），
不必为它先把原始值搬过 IPC。

**BIN 不做整列**：16 字节就是 128 个 0 / 1，一面墙。bit 级信息只在两处承重，各给各的呈现：基数缓存最高位的失效标记
（字段表单独标出）、6-bit 与字节边界的错位（上面那个三字节示意，顺带回答「为什么这块 hex 没法读」）。

### 不提供原始字节编辑

健康态与回退态都**只读**，抽屉标题挂「只读」tag。裸编辑保存即损坏，这正是「首先是防损坏」要堵的路径；
损坏值编辑后保存也只是以另一种方式损坏。真要改字节，CLI（`GET` / `SET`）是正当入口——回退态的状态行把这句话
写出来，而不是留一个禁用按钮让人猜。

## 不做

- **把 HLL 升格为第七种类型**（`KEY_TYPES` 加 `hyperloglog`、配一个类型色）。SCAN 付不起识别成本，于是树上显示 string、
  打开后变 HLL，类型色的三个出现点自相矛盾；所有按 `TYPE` 分支的路径都得加特例。半升格的类型是永久性的不一致。
- **`PFMERGE` 进界面。** 跨 key 操作、集群下受 `CROSSSLOT` 约束、低频，还得配一个 key 选择器。CLI 是它的正当入口，
  仪表盘的说明里写明了。
- **原始字节编辑，或一个禁用的编辑按钮**，见「不提供原始字节编辑」。
- **BIN 整列**，见「染色与 BIN」。
