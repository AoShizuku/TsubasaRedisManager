# Key 树

覆盖：`src/lib/keyTree.ts`、`src/styles/tree.css`、`src/stores/sessions.ts`（展开态 `expandedPaths`；搜索：`startSearch`、`cancelSearch`、`probeExactKey`、`setSearchTasksPaused`；前缀扫描与权威：`scanPrefix`、`canScanPrefix`、`isCountExact`、`authoritativePrefixes`）、`src/components/sidebar/sidebarRows.ts`、`src/components/sidebar/KeyTree.vue`（行网格、分段命中、计数徽标、TTL 标记、搜索态行、「在此搜索」「扫描此前缀」入口）、`src/components/sidebar/Sidebar.vue`（模式切换与紧凑开关、漏斗弹层、搜索框、前缀作用域 chip、窗口隐藏暂停）、`src/stores/settings.ts`（`compactPaths`、`indentGuides`、`treeTtl`、`defaultTreeMode`）、`src/lib/format.ts`（`formatPartialCount`、`formatApproxPercent`）

侧栏是整个应用唯一的导航区：`连接 → DB → namespace → key` 在同一棵树里，不做二级抽屉。
它也是性能压力最大的地方，虚拟化与数据层的约束见 [architecture](../architecture.md)「性能敏感区」。

## 行网格与对齐

**所有节点类型共用同一套列网格。** 同一深度的文件夹和 key，标签起始位置必须完全相同，
否则视线在垂直扫描时会左右抖动。

```
│ 左边距 │ 缩进 × depth │ 箭头槽 │ 间距 │ 图标槽 │ 间距 │ 标签 ……………… │ 计数 │ 右边距 │
```

各段宽度以 `tree.css` 的 `.trow`、`.tw` 为准（树的网格没有令牌）。depth 是 `useSidebarRows` 合成后的深度——
连接 0、DB 1、key 树第一层 2——渲染时直接作为 `--ind`。

- **箭头槽**：无子节点时留空但**必须占位**，否则叶子节点的标签会左移一格。
- **图标槽**与 12px 图标同宽，内容居中：DB / namespace 是 `database` / `folder` / `folder-open` 图标；
  连接是颜色圆点，key 是类型色点，圆点靠左右外边距补齐到图标槽宽。
  **色点不能裸放**：裸点比图标窄，key 名会比同深度的文件夹名靠左，整棵树的标签列参差不齐。
- **计数**右对齐到内容区右边界。
- 行高是 `--h-tree`，随密度（设置 → 外观 → 行高密度）切换；虚拟化的 JS 里还有一份，见
  [architecture](../architecture.md)「行高有两份」。

**孩子永远左对齐、相对父节点缩进一级。** 树里任何形式的右对齐正文都是错的：
右对齐会破坏「缩进即层级」这条唯一的视觉线索。只有元数据（计数、TTL 标记、状态）可以右对齐。

### 缩进参考线

深度一深，仅靠 x 位置判断从属关系就不可靠了。每一级祖先画一条 1px 竖线（`--bd`），
落在那一级箭头槽的中心线上（`.trow::after`）。默认开启，开关在侧栏漏斗弹层与设置 → 外观 → Key 树（`indentGuides`）。
列表模式下不画。

## 紧凑路径

> 界面上叫「紧凑」，不叫 Hybrid——Hybrid 会被理解成「树形与列表的混合」，那是另一个维度。
> 它等同于 VS Code 的 `explorer.compactFolders`、JetBrains 的 compact middle packages。

连续的**单子节点**链合并为一行，一直合并到第一个拥有多个子节点的层级为止（`flattenTree` 里的 `collapseChain`）。
末端如果是单个 key，也一并合并进来——Redis 里 `lock:job:88213`、`user:1001:profile`
这种「命名空间下只有一个 key」的形态极其常见，为它单独占一行加一级缩进是纯亏损。
自身既是 key 又有子节点的节点不往下合并：它得保留自己的身份。

```
朴素树                              紧凑后
▾ user                             ▾ user
  ▾ session          264             ▾ session              264
    ▾ 9f2c41ab         1                 9f2c41ab:meta:v2
      ▾ meta            1
          v2
```

5 行 4 级缩进 → 1 行。

### 分段命中

合并行的每一段必须独立可 hover、可右键，否则中间层级就失去了操作入口——
这是 compact folders 唯一被诟病的地方。

- 分隔符用 `--fg-4` 压暗（`.tsep`），段落文字用正常色。
- hover 时指针下的那一段单独加深（`.tseg:hover`），看得出右键会落在哪一段。
- 右键单段：菜单标题显示该段的完整前缀，前缀那一组操作（在此搜索、扫描此前缀、在 Key 浏览器中打开、
  批量设置 TTL、批量删除等，以 `KeyTree.vue` 的菜单为准）作用于这个前缀。右键 `cache:page` 的 `cache` 段拿到的是 `cache:*`。
- 类型色点仍在行首：整行在语义上仍是一个 key 行。

### 左键属于整行，分段只承担右键

**点合并行的任何一段，做的都是这一行的主操作**：key 行打开 key，namespace 行折叠 / 展开。
分段身份只在右键时才有意义。不让左键按段分派（点末端段打开 key、点中间段展开该层），两个原因：

1. **中间段没法独立展开。** 合并行的中间层按定义是单子节点链，决定这一行展不展开的是最深那个节点
   （`cache:page`），把 `cache` 加进展开集对渲染毫无影响。点中间段只会是个什么都不发生的空转。
2. **末端段可能点不到。** `chat:info:4ae982a2-f958-…` 这种行，前缀一长末段就被挤出可视区；
   要是只有末端段能打开 key，左键点在别处毫无反应，看起来就像坏了。

箭头槽 `@click.stop`，「只想折叠不想打开」仍然做得到。既是 key 又是前缀的行（`user` 与 `user:1` 并存）
点名字打开 key、点箭头展开子树——不能因为它有子节点就退化成折叠，否则这个 key 永远打不开。

键盘导航下选不中中间段，← 折叠整行。VS Code 有同样的限制，可以接受。

### 默认开启，不做成第三个模式

模式切换保持 `树形 / 列表` 二选一，紧凑是树形模式下的开关（`compactPaths`），**默认开启**。
三选一要求用户先理解三个概念才能选，而紧凑相对朴素树在几乎所有情况下都是净胜。

开关是**侧栏模式切换行里的常驻小按钮**，紧挨着 `树形 / 列表`。它的效果要「开一下关一下对比」才能理解，
藏进漏斗弹层会让对比成本变高；漏斗弹层留给 SCAN COUNT、树节点上限这类一次性设定。
设置 → 外观 → Key 树里是同一个开关。列表模式下按钮置灰。

**搜索时紧凑会自然退化成扁平列表**——过滤后几乎每层都只剩单子节点。等于免费得到「搜索结果自动变平」，
这是默认开启的最强论据。

### 增量到达会改变合并结果

SCAN 是增量到达的：某个命名空间此刻只有 1 个 key，下一批又来 3 个，合并行就得裂开。

- **行状态一律按完整前缀存，不按行索引**：展开态（`expandedPaths`）、选中项、前缀权威集。
  裂开之后行索引全变，前缀不变。
- 展开合并行时，被合并掉的中间层一起标记为展开（`expandRow`、`TreeRow.mergedPaths`）。
  否则裂开之后，已经展开的子树会突然藏起来。
- 没有滚动锚定，也不对仍在加载的分支延后合并：结果流入时，正在看的行可能被挤走。
  见 [backlog](../backlog.md)「扫描结果流入时树会跳」。

## 计数

树上的数字有两种来源，含义完全不同：

| 行 | 来源 | 精确性 |
|---|---|---|
| DB | `dbLists` 里的 key 数（`INFO keyspace` / `DBSIZE`） | 精确、廉价，不带 `+` |
| namespace（以及既是 key 又是前缀的行） | 已加载 key 的统计（`KeyNode.keyCount`） | **部分值** |

部分值带 `+`（`formatPartialCount`）：没扫完时显示 `312+`，全库扫完或该前缀成为权威后才显示 `312`。
直接显示部分值会让人读成「这个命名空间就 312 个 key」，见「部分视图」。摘 `+` 的条件见「前缀权威」，
`N+` 的 tooltip 与点击见「诚实信号」。

**空间不足时先压计数，名字永远优先**（`.tcount` 的收缩系数远大于名字）。为了保住一个次要数字去截断名字，是把优先级搞反了。

## 树里默认不显示 TTL

每个 key 显示 TTL，意味着每个 key 多一条 `TTL` 命令。类型色点已经付了一次 `TYPE` 的代价，
再翻倍在大 keyspace 上不划算。所以它是设置项（`treeTtl`：设置 → 外观 → Key 树 → 显示 TTL 标记，
漏斗弹层里也有），**默认关闭**；开启后扫描带 `withTtl`，与 `TYPE` 走同一批 pipeline。

开启时的呈现：

- 每个有过期时间的 key 行都有，不是选中行的孤例；不过期的不显示——那是绝大多数 key 的状态，显示出来只是噪声。
- 带边框的小 chip（`.tttl`），**刻意不与计数同形**：同槽位同字重的话，`23:41` 会被读成「41 个」。
- 不超过即将过期阈值（`ttlSoonThreshold`）的标成琥珀色，与标签页的 TTL chip 同一个阈值。
- 读数是扫描那一刻的快照，不倒数。实时读数在标签页的 TTL chip 上，见 [ttl](ttl.md)。

## 列表模式

`树形 / 列表`（`defaultTreeMode`，侧栏模式切换与设置 → 外观 → Key 树）。列表模式是去掉命名空间层级的 key 列表：
名字加类型点，用于浏览跨命名空间的搜索结果。实现上是用空分隔符建树、关掉紧凑合并（`useSidebarRows`），
不另走一套渲染路径。key 仍挂在 DB 下面缩进一级，那一级从属关系还在；参考线不画。

它不带内存、编码这类列，因此放得进侧栏。要按列排序用 Key 浏览器，见 [key-browser](key-browser.md)。

## 部分视图

SCAN 是对整个 keyspace 的无序采样：每个文件夹的内容随全库扫描进度随机到达。而文件夹这个隐喻自带承诺——
打开就是完整内容。用户带着文件管理器的心智模型来，默认「所见即全部」，于是在一个没扫全的文件夹里翻半天，
得出「这个 key 不存在」的错误结论。

所以树在没扫完时是**部分视图**，界面守两条：

- **「没有匹配」与「还没扫到」是两句话。** 不完整的列表绝不能长得像完整的。搜索才扫了一批就显示一棵空树，
  用户读到的是「没有结果」，实际含义是「才扫了 0.02%」。
- **补全的成本不压在用户手上。** 提示只治误判，治不了找不到：一次几百个的点击式分页，在百万级库里找一个 key
  意味着上千次点击。

三种诉求各有落点：

| 诉求 | 用户要的 | 落点 |
|---|---|---|
| 查找 | 知道 key 名的一部分，要结果，不关心过程 | 「搜索」 |
| 浏览 | 在某个文件夹里逛，要这个局部是权威的，至少明确告诉他不权威 | 「文件夹内搜索与前缀权威」 |
| 诚实 | 底线 | 「诚实信号」 |

## 搜索

搜索框有输入（防抖后）就启动 `search_keys` 任务（`startSearch`）：后端扫到游标归零，key 经
`redis://task-progress` 流式并入会话的 `keys`，树随之重建。**查找不该有手动推进的分页**，所以搜索没有「加载更多」。
后端那一半见 [backend/tasks](../backend/tasks.md)「扫到底的扫描任务」。

模式拼法：输入含 `*` 就原样下发，否则包成 `*词*`（`scopedSearchPattern`）。词**不转义**，见「前缀生成模式必须转义 glob 元字符」。

### task_id 就是代际令牌

每次搜索开一个新任务。旧任务没消费完的事件带着旧 `task_id` 到达时已经没人订阅，自然丢弃，不另造代际机制。
`SearchRuntime.epoch` 是它在本地的影子，只为覆盖 `startSearchKeys` 还没返回 id 的窗口期：这段时间里输入又变了，
拿到 id 后立刻取消那个没有消费者的任务。

浏览路径（`scanMore`）没有 `task_id`，靠 `Session.scanGeneration`。

### 取消时机

以下任一发生都取消当前搜索任务（`teardownSearchTask`）：

- 输入变更（防抖后起新任务）、清空输入（回浏览态重扫）；
- 切换活动会话（`cancelSearch`）——看不见的会话不该继续烧服务端；
- 关闭会话——先取消再断连，否则任务要等下一页失败在连接关闭上才停；
- 结果触到 `treeNodeLimit`；
- 取消按钮。状态栏的停止按钮从外部取消，落成「已取消」。

**取消是义务，不是优化。** 只停止消费、不通知后端，服务端会继续全速扫，喂给一个正在丢弃结果的客户端。
上限路径因此是**取消任务**并显示「已达上限（N），请细化模式」，而不是弹一句提示、让任务在后台跑完：

> 不显示的东西就不要再去取。

窗口隐藏时**暂停**（不是取消）所有扫描类任务，可见时恢复（`setSearchTasksPaused`），恢复后从当前游标继续。
暂停广播只够得着已有 `task_id` 的任务；启动在途的任务拿到 id 后按期望态（`scanTasksPaused`）补发一次——
否则窗口恰好在启动间隙隐藏，那个任务会全速跑到底。

### 搜索态

`Session.searchStatus` 不是 `'idle'` 即搜索态：

- **「加载更多」行不出现。** 任务自己扫到底，没有「更多」可点，底部行换成任务状态（见「诚实信号」）。
  `scanMore` 在搜索态直接返回：两条管线不许往同一个数组里写。
- **刷新落在搜索态 = 重启搜索任务。** 刷新按钮、右键「重新扫描」不带模式调 `rescan`，搜索态下它分派给 `startSearch`。
  否则会造出「搜索模式 + 加载更多（已加载 N）」的杂交态：搜索结果只扫了一批，却长得像可以手点续扫的浏览视图。
- **合帧。** 任务每页一个事件，逐事件重建树是 O(n) × 页数。结果先进 `SearchRuntime.buffer`，按帧 flush 一次
  （`scheduleSearchFlush`）。缓冲刻意不进 reactive，否则合帧白做。窗口转入隐藏时同步清账：隐藏窗口里 rAF 不跑，
  最后几页会一直滞留到重新可见。
- 结果按 key 名去重（`SearchRuntime.seen`）：SCAN 在 rehash 期间会重复返回同一个 key。
- 搜索结果不需要新的呈现模式：紧凑路径自然把它摊成扁平列表，见「默认开启，不做成第三个模式」。
- 切会话时搜索框恢复成该会话自己的原词（`Session.searchQuery`），不是拼好的模式——作用域已经在 chip 里，
  回填整个模式会把前缀重复一遍。

### 精确命中

输入不含 glob 元字符（`* ? [ ] \`，`GLOB_META`）时，它可能就是完整 key 名：在扫描任务之外**并行**探测一次
（`probeExactKey`，一次 `getKeyMeta`），命中就在结果顶部置顶一行「精确命中」，点击即打开。
知道完整 key 名的人不用等扫描。

- 作用域下候选是「前缀 + 分隔符 + 词」。元字符只看词：前缀是树里的字面路径。
- 置顶行是这个 key 的唯一呈现：已经流进来的摘掉，还没来的用 `seen` 挡住。「已找到 N 个」把它算进去；
  有精确命中时不显示「没有匹配的 Key」。
- 探测失败不打扰扫描主线，只是少一行置顶。
- **明确放弃的边缘**：key 名本身含 glob 元字符且用户原样输入——它被当作模式，字面命中靠扫描兜底。

## 文件夹内搜索与前缀权威

「在文件夹里找 key」时，用户手里往往只有文件夹：没有词，或者词在别的前缀下也大量命中，全局搜索帮不上。两个入口：

| 入口 | 模式 | 树的状态 |
|---|---|---|
| 右键 namespace（含合并行的任意一段）→「在此搜索」 | `scopedSearchPattern(前缀, 分隔符, 词)` | 进搜索态，搜索框出现前缀 chip（`Session.searchScope`）；词为空就是这个前缀扫到底的搜索结果 |
| 点文件夹的 `N+` 计数，或右键「扫描此前缀」 | `matchPatternFor(前缀, 分隔符)` | 留在浏览态，`load_all_keys` 任务的结果叠加进已加载的树（`scanPrefix`） |

「在此搜索」复用整条搜索管线，文案、取消时机、上限、暂停都不另写。前缀与分隔符转义，词照全局搜索的规则。
清除 chip（点 ×，或在空输入框里按 Backspace）：词还在就退回全局搜索，词空就回浏览态（`clearSearchScope`）。

### 前缀权威

「扫描此前缀」完成后，该子树成为**权威视图**：计数摘掉 `+`，显示精确值（`isCountExact`）。

- 权威集按**完整前缀**存（`authoritativePrefixes`），不按行索引：紧凑合并行裂开后行索引会错位，与展开态同一个道理。
  包含关系对子前缀成立——`user` 权威则 `user:profile` 也权威；判定逐级剥段查集合，只认整段边界，
  `user` 不会覆盖 `userx:1`（`isPrefixCovered`）。
- 会话内存态，不持久化。作废时机：重新扫描、进搜索态、keyspace 版本号递增（批量操作改了一个范围，`invalidateKeyspace`）、
  会话关闭。全库扫完（`scanComplete`）后所有前缀天然权威，集合清空即可。
- **只有 `completed` 置权威。** 取消、失败只清进行中标记。触到 `treeNodeLimit` 与搜索同一条规则——取消任务、
  不置权威：没并进来的部分让这个前缀依然不完整，摘 `+` 就是撒谎。
- 扫描进行中该行的计数位换成 spinner（`scanningPrefixes`）。紧凑合并行看每一段：右键中间段发起的扫描也要在这一行上有反馈。
- 叠加层是与浏览续扫并行的第二条写入管线，两边并入时都按 key 名去重：叠加层以任务启动时的 `keys` 为基线
  （别的写入者动过 `keys` 就重建基线），浏览续扫每批临时建集合去重。
- 「扫描此前缀」在搜索态、树已到上限、计数已精确、正在扫描时不可用，禁用时 title 说明原因（`canScanPrefix`、`scanPrefixHint`）。
  搜索态下禁用，是因为不允许两条管线同时往一个会话灌 key；树已到上限时再扫也只会被立刻取消。

## 诚实信号

**浏览态底部行**写「加载更多（已加载 20,000 / 2,140,000）」。分母是 DB 行上本来就在显示的 DBSIZE（`dbLists`），
拿不到时只写已加载数。部分视图长得和完整视图一模一样，这个比值是视口里唯一说出「这里不全」的地方。

**底部行的文案矩阵**——「没有匹配」与「还没扫到」必须是两句话：

| 状态 | 底部行 |
|---|---|
| 浏览 · 扫描中 | 正在扫描… |
| 浏览 · 未扫完 | 加载更多（已加载 N / DBSIZE） |
| 浏览 · 触到树节点上限 | 已达树节点上限（N / DBSIZE），继续加载 |
| 浏览 · 扫完 · 空库 | 这个数据库是空的 |
| 搜索 · 进行中 | 已找到 N 个 · 扫描中… 约 P%　［取消］ |
| 搜索 · 扫完 · 零结果 | 没有匹配的 Key |
| 搜索 · 扫完 · 有结果 | 无底部行，计数摘 `+` |
| 搜索 · 达上限 | 已达上限（N），请细化模式 |
| 搜索 · 已取消 | 已找到 N 个 · 已取消 |
| 搜索 · 失败 | 已找到 N 个 · 扫描失败 |

文案以 `KeyTree.vue` 与 `sidebarRows.ts` 为准。几条约束：

- **「已找到 0 个 · 扫描中…」绝不能长得像「没有结果」。** 「没有匹配的 Key」只在扫完时出现：
  搜索态下就是任务 `completed`，那时才置 `scanComplete`。
- `completed` 与 `cancelled` / `failed` 是不同的状态（`SearchStatus`）：前者权威，后两者不完整，必须说出停在了哪。
- 任何搜索态下都不出现「加载更多（已加载 N）」。搜索态的「已加载 N / M」也没有分母：MATCH 下 N 数的是命中数，
  除以全库大小没有意义。
- 进行中的百分比是后端从 SCAN 游标估算的近似值，**必须带「约」**，估算不可用时不显示、只留不定进度。
  这条集中在 `formatApproxPercent`：取整用 floor 并封顶 99——任务还在跑，「约 100%」自相矛盾，真正的完成由终态表达。
  为什么拿不到精确分母见 [backend/tasks](../backend/tasks.md)「扫描任务：只报命中数」。
- 取消按钮用蓝色：终止搜索不丢已有结果，不是危险操作。

**`N+` 的 tooltip** 写「扫描未完成，实际数量可能更多。点击扫描此前缀。」——它同时是「扫描此前缀」的发现路径。
不可点时（搜索态、树已到上限）只说前半句，不许诺一个按不动的动作。

## 前缀生成模式必须转义 glob 元字符

树上的 namespace 段是字面路径，而 SCAN 的 MATCH 是 glob：服务端的 `stringmatchlen` 认 `* ? [ ] \`。
从前缀拼模式时（`matchPatternFor`、`scopedSearchPattern` 的前缀部分），前缀与分隔符都先过 `escapeGlob`，
否则 key 名里的元字符会把前缀变成另一个意思：

```
库里有：evil[ab]:1   与   evila:1
未转义   evil[ab]:*    → 命中 evila:1，扫不到 evil[ab]:1
转义后   evil\[ab\]:*  → 只命中 evil[ab]:1
```

`[ab]` 成了字符类。右键 `evil[ab]` 这一段，用户要的是它下面那一片；不转义的话**两头都错**——
在「在 Key 浏览器中打开」上是列表不对，在批量删除上是删掉一个无关的 key、同时漏掉他右键的那一片。
这一条由真实服务端钉住：`tests/redis_phase5b.rs` 的
`scan_only_matches_the_literal_prefix_when_glob_metacharacters_are_escaped`。

**转义的边界是「从前缀生成模式」这一步。** 用户手输的部分不转义——批量对话框的模式框、
搜索框里的词，那里他要的就是 glob。这条边界要守住，否则 `cache:*` 会被转义成一个永远匹配不到东西的字面串。

转义之后，「前缀 + 分隔符 + `*`」的语义恰好是「以这个字面前缀开头」。批量删除完成后按字面前缀
`startsWith` 裁树，正是依赖这一点，见 [batch](batch.md)「删完裁树」。

## 不做

- **紧凑路径做成第三个模式。** 见「默认开启，不做成第三个模式」。
- **左键按段分派**（点末端段打开、点中间段展开）。中间段展不开、末端段可能点不到，见「左键属于整行，分段只承担右键」。
- **树里默认显示 TTL。** 每 key 多一条命令，见「树里默认不显示 TTL」。
- **把醒目提示当主修复。** 治误判不治找不到，补全成本仍在用户手上。见「部分视图」。
- **打开 DB 就自动扫到 `treeNodeLimit`。** 无条件消耗 WAN 带宽与 Redis CPU，而用户可能下一秒就去搜索；
  扫到两万个对两百万的库依然不权威。浏览的可信度靠「诚实信号」，边际收益撑不起无条件成本。
- **把浏览续扫当成「无限滚动」。** 机械上像，语义上不成立：SCAN 无序采样，新 key 不追加在底部，而是插进已排序树的
  任意位置，增量到达还会改变紧凑合并的结果——「上面看过的部分不会变」这个隐含契约在这里是假的。
  浏览续扫只能省点击，不承诺完整性；完整性的答案是「搜索」与「文件夹内搜索与前缀权威」。
  视口触发续扫见 [backlog](../backlog.md)「浏览态续扫只能手点」。
- **给搜索另造代际令牌。** `task_id` 已经是，见「task_id 就是代际令牌」。
- **对搜索词做 glob 转义。** 与「用户手输的模式不转义」冲突：同一个词在全局搜索框与前缀作用域里语义不同，
  比元字符伤到新手更糟。要改就是所有搜索入口一起改成「字面搜索 + 显式 glob 开关」，不给单一入口开特例。
- **按节点惰性加载作为主加载机制。** 服务端没有「枚举某前缀的直接子级」的能力，惰性加载一个文件夹等于
  `MATCH 前缀*` 把全 keyspace 扫一遍；顶层有哪些文件夹本身就得先全局扫才知道。分页粒度（DB）与导航粒度（文件夹）
  确实错位，但前缀扫描是对齐它的**叠加层**，不替换全局扫描。
- **搜索结果暂无类型点。** 类型点是三处类型色之一，搜索结果正是用户盯着看的部分。所以扫描任务的事件项自带类型，
  见 [backend/tasks](../backend/tasks.md)「事件项带 keyType」。
