  • 末端的单个 key 也一并合并。Redis 里 lock:job:88213、user:1001:profile 这种"命名空间下只有一个 key"的形态极其常见，为它单独占一行加一级缩进是纯亏损——这正是 VS Code explorer.compactFolders 的思路。
  • 分段命中是成败关键。合并行的每一段独立可 hover、可右键（图中 cache:page 的 cache 段处于 hover 态）。右键某段，菜单作用于该段的完整前缀 cache:*；不做分段命中的话，中间层级就彻底失去了批量操作的入口。
  • 默认开启，不做成第三个模式。模式切换保持"树形 / 列表"二选一，紧凑是树形下的开关。三选一要求用户先理解三个概念才能选，而紧凑相对朴素树在几乎所有情况下都是净胜。
  • 附带好处：搜索/筛选时压缩会自然退化成扁平列表，因为过滤后几乎每层都只剩单子节点。
  • 实现陷阱：SCAN 增量到达会让合并行裂开。折叠状态必须按末段的完整前缀存储而不是按行索引，否则裂开后整体错位；滚动位置要以当前聚焦行为锚点。
Key 浏览器：为什么它在主区而不在侧栏
  • 侧栏只有 268px，塞不下"类型 / TTL / 内存 / 编码"四列可排序表格。硬塞的结果是每列都截断，排序也失去意义。
  • 两者的用途本来就不同：树形用来「逛」，表格用来「查」——按内存降序找大 key、按 TTL 升序找快过期的 key。这两件事在树里做不到。
  • 代价必须显式化。TTL 与内存两列需要对每个 key 额外执行 TTL 和 MEMORY USAGE，所以"分析模式"是一个带成本提示的开关，不是免费默认项。关闭时只显示 Key 与类型两列，走 redis_scan_keys 已有的返回值。
  • 底部明确写出"排序只作用于已加载部分"。对 128 万 key 的 keyspace 做全量排序需要先全量加载，界面不能假装已经排好了。

  • 主入口是标签栏的 + 下拉（图中已展开）。它一次解决全部六个非 key 标签页的入口——02 里那个 CLI 标签页此前同样没有来路。菜单底部常驻显示新标签页的作用域，避免在 A 连接的上下文里开出连到 B 的 CLI。
  • 上下文入口让它和树连起来：右键 namespace（含紧凑合并行的单个段）→ 在 Key 浏览器中打开，MATCH 自动填 cache:*。这让分段命中有了第二个用武之地——树负责定位，表格负责分析，两者用同一个前缀串起来。
  • 另外两个上下文入口：侧栏搜索出大量结果时，计数旁出现「在表格中查看」；点击状态栏的内存读数直接打开浏览器并按内存降序排——那个数字目前只是个死读数，可点击就成了排查大 key 的最短路径。
  • 标签标题必须带作用域：Key 浏览器 · db0、CLI · prod-east。SCAN 本身按 connection + DB 隔离，同时开 prod-east/db0 和 staging/db3 两个浏览器是常见需求。
  • 只读连接下 Key 浏览器、Monitor、订阅、内存分析照常可用（都是读操作），菜单里需要置灰的只有「导入」，并在 tooltip 里说明原因。
树的另外两处修正
  • 缩进参考线：深度 ≥ 3 时仅靠 x 位置已经判断不出从属关系。每条线落在祖先层箭头槽的中心线上，用 --bd 色。
  • 计数语义：user 显示 312+ 而 profile 显示 48——加号表示该分支的 SCAN 尚未完成，这只是已加载部分的统计。DB 层的 1,284 来自 DBSIZE，是精确值。ARDM 在这里一律显示部分值，会造成"这个命名空间就 312 个 key"的误判。
